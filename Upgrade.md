# Техническое задание: интеллектуальный менеджер моделей для ProstoVoice

## 1. Цель

Реализовать в Android-приложении ProstoVoice систему управления моделями распознавания речи, которая самостоятельно обеспечивает наличие хотя бы одной полностью готовой к работе модели.

**Главный принцип UX:** пользователь должен иметь возможность записать или импортировать аудио и получить расшифровку, не разбираясь в названиях моделей, форматах файлов, размерах весов, движках распознавания и настройках нейросетей.

Приложение самостоятельно отвечает за:
- наличие рабочей модели распознавания;
- загрузку или импорт дополнительных моделей;
- проверку целостности файлов;
- подготовку модели к запуску;
- регистрацию модели в системе;
- выбор подходящей модели;
- безопасное переключение между моделями;
- удаление ненужных моделей без потери работоспособности приложения.

## 2. Исходные условия и ограничения

В проекте уже используются встроенные компоненты:
- **Whisper** — встроенная модель распознавания речи;
- **sherpa-onnx** — компоненты, используемые для диаризации.

Их необходимо сохранить и учитывать при реализации Model Manager.

Обязательные условия:

1. Приложение должно работать без подключения к интернету.
2. Уже установленная встроенная модель должна быть готова к использованию без дополнительных действий со стороны пользователя.
3. Загрузка дополнительных моделей должна происходить только для последующего локального использования.
4. Аудиозаписи, расшифровки и результаты диаризации не должны отправляться на внешние серверы.
5. Распознавание и диаризация должны выполняться локально на устройстве.
6. Нельзя допустить состояния, в котором приложение осталось без рабочей модели распознавания.
7. Нельзя удалять обязательные компоненты диаризации, пока не подготовлена и не проверена полноценная замена.

## 3. Пользовательский сценарий и интерфейс

### 3.1. Основной сценарий

При первом запуске пользователь не должен видеть предложение скачать модель или выбирать её самостоятельно.

Приложение:
1. Проверяет наличие встроенной модели.
2. Проверяет, готова ли она к работе.
3. При необходимости выполняет первичную подготовку.
4. Делает её основной моделью распознавания.
5. Показывает пользователю обычный интерфейс приложения.

Пользователь сразу может импортировать аудиозапись или начать запись и запустить транскрибацию.

### 3.2. Работа с дополнительными моделями

Управление дополнительными моделями располагается в настройках приложения в отдельном разделе, например «Модели распознавания».

Не следует делать этот раздел центральной частью интерфейса.

В обычном режиме пользователь должен видеть только понятную информацию:
- распознавание готово;
- модель подготавливается;
- требуется подключение к интернету для загрузки;
- не удалось подготовить модель;
- используется резервная модель.

Не показывать без необходимости технические названия форматов, движков, файлов и архитектур моделей.

### 3.3. Каталог дополнительных моделей

В приложении необходимо предусмотреть каталог моделей, доступных для установки.

На текущем этапе планируются следующие варианты:

- **Parakeet** — различные размеры и варианты моделей;
- **Whisper** — различные размеры и версии;
- **GigaAM v3**;
- **GigaAM v3 Multilingual**.

GigaAM v3 и GigaAM v3 Multilingual должны отображаться в каталоге как отдельные варианты моделей, которые можно независимо установить, подготовить, выбрать и удалить с соблюдением общих ограничений.

Каталог должен поддерживать расширение: добавление новых моделей в будущем не должно требовать переработки всей системы управления.

Для пользователя каталог должен выглядеть как список доступных улучшений распознавания, а не как файловый менеджер.

Для каждой модели можно отображать:
- понятное название;
- короткое описание;
- ориентировочный размер загрузки;
- состояние доступности;
- состояние установки.

Технические детали модели должны оставаться в метаданных и не перегружать обычный интерфейс.

### 3.4. Автоматический выбор модели

В стандартном режиме приложение самостоятельно выбирает подходящую модель.

При выборе учитывать:
- совместимость модели с устройством;
- доступную оперативную память;
- требования к вычислительным ресурсам;
- поддерживаемый формат модели;
- наличие соответствующего runtime;
- успешность предыдущей инициализации;
- предполагаемый баланс качества и скорости;
- поддерживаемые языки и возможности конкретной модели.

Пользователь не должен самостоятельно сравнивать веса моделей и выбирать backend.

Правила выбора:
1. При первом запуске использовать проверенную встроенную модель.
2. Не переключаться на дополнительную модель до окончания её полной проверки и инициализации.
3. Не заменять текущую рабочую модель на неподготовленную или несовместимую.
4. Если новая модель не запускается, продолжать использовать предыдущую.
5. При необходимости автоматически возвращаться к последней рабочей модели.

Ручной выбор модели допускается в дополнительных настройках, но не должен быть обязательным для обычного использования.

## 4. Загрузка и подготовка модели

Загрузка модели — это только один из этапов её установки. После загрузки модель должна быть полностью подготовлена к использованию.

### 4.1. Источники моделей

Необходимо поддержать два способа добавления модели:

**A. Из каталога приложения**
- получение метаданных модели;
- загрузка необходимых файлов;
- проверка целостности;
- регистрация;
- инициализация соответствующего движка.

**B. Импорт собственной модели**
- пользователь выбирает файл или набор файлов через системный Android Storage Access Framework;
- приложение копирует файлы в собственное внутреннее хранилище;
- проверяет структуру и совместимость;
- определяет, какие компоненты и runtime необходимы;
- регистрирует модель;
- выполняет инициализацию.

Не следует считать любой выбранный файл полноценной моделью. Необходимо проверять, что импортированного набора файлов достаточно для запуска поддерживаемого backend.

Если формат не поддерживается, показать понятную ошибку и не регистрировать модель как готовую.

### 4.2. Этапы установки

Каждая модель должна проходить последовательные этапы:

1. `NOT_INSTALLED` — модель отсутствует.
2. `DOWNLOADING` или `IMPORTING` — загрузка или импорт файлов.
3. `VERIFYING` — проверка целостности и состава файлов.
4. `REGISTERING` — регистрация модели в локальном реестре.
5. `INITIALIZING` — подготовка соответствующего движка и проверка запуска.
6. `READY` — модель полностью готова к работе.
7. `FAILED` — установка или подготовка завершилась ошибкой.

Модель получает статус `READY` только после успешной инициализации и проверки реального запуска.

**Важно:** наличие файлов на устройстве не означает, что модель готова к использованию.

### 4.3. Загрузка

Реализовать:
- отображение прогресса загрузки;
- отображение объёма загруженных данных;
- возможность отменить загрузку;
- обработку потери подключения;
- корректную обработку нехватки места;
- защиту от повреждённых и неполных файлов;
- возможность безопасно повторить загрузку после ошибки.

Файлы следует загружать во временную директорию. Перемещать их в постоянное хранилище и регистрировать модель только после успешной проверки.

Загрузка должна выполняться по HTTPS. Для моделей из каталога использовать контрольные суммы из доверенных метаданных. Не считать наличие корректного имени файла подтверждением его целостности.

### 4.4. Подготовка

После загрузки или импорта приложение должно автоматически:
- проверить обязательные файлы;
- проверить совместимость формата;
- проверить наличие нужного runtime;
- подготовить конфигурацию;
- проверить доступность ресурсов;
- инициализировать backend;
- выполнить тестовый запуск;
- зарегистрировать модель как готовую.

Пользователь не должен вручную перемещать файлы, редактировать конфигурации или указывать пути к весам.

Если модель требует отдельного runtime, например не может работать через существующую интеграцию Whisper, необходимо реализовать настоящий адаптер соответствующего движка.

**Запрещено:** регистрировать Parakeet или GigaAM как Whisper-модель только ради того, чтобы они отображались в списке. У каждого семейства должна быть реальная поддержка соответствующего формата и backend.

## 5. Архитектура Model Manager

Реализовать отдельный компонент управления моделями, не смешивая его ответственность с логикой транскрибации.

Рекомендуемое разделение:

### 5.1. ModelCatalog

Отвечает за:
- список доступных моделей;
- получение метаданных;
- версии моделей;
- ссылки на файлы;
- контрольные суммы;
- требования к устройству;
- информацию о совместимом backend.

Метаданные должны позволять добавлять новые модели без переписывания основной логики Model Manager.

### 5.2. ModelDownloader

Отвечает за:
- загрузку файлов;
- прогресс;
- отмену;
- обработку сетевых ошибок;
- повторные попытки;
- проверку завершённости загрузки.

### 5.3. ModelImporter

Отвечает за импорт файлов из локального хранилища Android.

Должен использовать системный механизм выбора файлов и не требовать от пользователя прямого доступа к внутренним директориям приложения.

### 5.4. ModelVerifier

Отвечает за:
- проверку контрольных сумм;
- проверку обязательных файлов;
- проверку структуры пакета;
- проверку совместимости формата;
- выявление повреждённых и неполных моделей.

### 5.5. ModelRegistry

Хранит локальную информацию об установленных моделях:
- внутренний идентификатор;
- название;
- семейство;
- версия;
- backend;
- путь к файлам;
- размер;
- источник установки;
- статус;
- состояние инициализации;
- признак встроенной модели;
- дата установки.

Registry должен содержать только проверенные записи. Модель, которая не прошла подготовку, не должна считаться доступной для транскрибации.

### 5.6. ModelInitializer

Отвечает за подготовку и запуск модели через соответствующий backend.

Инициализация должна проверять не только существование файлов, но и фактическую возможность использовать модель.

### 5.7. ModelSelector

Отвечает за выбор текущей модели распознавания.

Должен:
- находить доступные готовые модели;
- учитывать совместимость;
- выбирать рекомендуемую модель;
- сохранять текущий выбор;
- переключать модель только после успешной подготовки новой;
- обеспечивать возврат к предыдущей рабочей модели.

### 5.8. ModelManager

Общий компонент, предоставляющий приложению единый API для управления моделями.

Другие части приложения не должны самостоятельно искать модели по именам файлов или собирать пути к весам.

## 6. Интеграция с существующим кодом

Перед реализацией изучить текущую архитектуру проекта.

В частности, проверить существующие:
- `TranscriptionOrchestrator`;
- `WhisperTranscriptionOrchestrator`;
- `NativePipeline`;
- `WhisperModelStore`;
- JNI-интеграцию Whisper;
- конфигурацию sherpa-onnx;
- места, в которых пути к моделям задаются напрямую.

Сейчас часть путей к моделям может быть задана жёстко. Необходимо заменить такую схему централизованным получением конфигурации из Model Manager.

Точные имена существующих файлов, конфигураций и методов необходимо проверить непосредственно в репозитории перед изменением. Не создавать новые имена наугад и не ломать существующие пути совместимости.

### 6.1. Интерфейс backend

Предусмотреть общий интерфейс для движков распознавания, например:

- проверка совместимости;
- инициализация;
- проверка готовности;
- выполнение транскрибации;
- освобождение ресурсов.

При этом конкретные реализации должны учитывать различия между движками.

Whisper, Parakeet, GigaAM v3 и GigaAM v3 Multilingual не обязаны использовать один и тот же внутренний формат или runtime.

Существующий контракт транскрибации и формат результата приложения необходимо сохранить либо изменить только при наличии обоснованной необходимости.

### 6.2. Сохранение диаризации

Диаризация должна оставаться отдельной подсистемой и не должна зависеть от того, какая модель ASR выбрана.

Встроенные компоненты sherpa-onnx необходимо сохранить.

Проверить фактические зависимости:
- модель сегментации;
- модель эмбеддингов;
- конфигурации;
- пути к файлам;
- runtime;
- код обработки результатов.

Если модель распознавания заменяется, это не должно автоматически менять или удалять модели диаризации.

Если для определённого способа диаризации необходимы дополнительные компоненты, их наличие тоже должно проверяться.

При невозможности корректно выполнить диаризацию приложение должно сохранять предусмотренную текущей архитектурой безопасную обработку ошибки, не ломая транскрибацию.

## 7. Удаление моделей

Реализовать удаление дополнительных моделей.

Основная логика должна защищать приложение от потери последней рабочей конфигурации.

### 7.1. Основные правила

1. Нельзя удалить последнюю готовую модель распознавания.
2. Нельзя удалить встроенную Whisper-модель, которая обеспечивает базовую работоспособность приложения.
3. Нельзя удалить обязательные компоненты sherpa-onnx, пока не существует и не проверена полноценная замена всей необходимой функциональности диаризации.
4. Нельзя удалить активную модель, пока не выполнено успешное переключение на другую готовую модель.
5. Нельзя удалять файлы модели, которая прямо сейчас используется активной транскрибацией.
6. Нельзя удалять компоненты, которые используются другой установленной моделью или подсистемой.
7. При ошибке удаления реестр и файловая система должны оставаться согласованными.

### 7.2. Встроенные компоненты

Встроенный Whisper необходимо сохранить как базовую модель.

Встроенный sherpa-onnx необходимо защищать отдельно от моделей распознавания.

Пользователь может менять основную модель распознавания на другую совместимую модель, но не должен получать возможность случайно удалить обязательную основу диаризации.

Если в будущем будет реализована полноценная альтернативная система диаризации, возможность замены её компонентов можно рассмотреть отдельно. В рамках текущей задачи удаление встроенных компонентов sherpa не требуется.

### 7.3. Удаление дополнительной модели

При удалении:
1. Проверить, что модель не используется текущей операцией.
2. Проверить, что после удаления останется хотя бы одна готовая модель распознавания.
3. Если модель активна, сначала переключиться на другую готовую модель.
4. Освободить ресурсы backend.
5. Удалить файлы модели.
6. Обновить локальный реестр.
7. Обновить интерфейс.

При невозможности безопасного удаления показать понятную причину.

## 8. Хранение файлов

Модели необходимо хранить во внутреннем хранилище приложения.

Рекомендуемая структура:

- `models/` — постоянные файлы моделей;
- `models/temp/` — временные файлы загрузки и импорта;
- `models/registry/` — локальные метаданные и состояние реестра.

Структуру можно адаптировать под существующую архитектуру проекта.

Требования:
- не хранить временные загрузки как готовые модели;
- не дублировать одни и те же файлы без необходимости;
- корректно обрабатывать отсутствие свободного места;
- не удалять исходную рабочую модель до успешной подготовки замены;
- учитывать совместное использование файлов несколькими конфигурациями;
- корректно обрабатывать перезапуск приложения во время загрузки или установки.

## 9. Обработка ошибок и восстановление

Необходимо предусмотреть обработку следующих ситуаций:

- нет интернет-соединения;
- загрузка прервана;
- файл повреждён;
- контрольная сумма не совпадает;
- не хватает места;
- формат не поддерживается;
- backend отсутствует;
- модель не инициализируется;
- устройство не соответствует требованиям;
- пользователь отменил импорт;
- приложение завершилось во время установки;
- модель удалена или повреждена вне штатного сценария.

Основное правило: **сбой при установке или переключении дополнительной модели не должен лишать пользователя возможности транскрибировать аудио.**

В случае ошибки приложение должно продолжать использовать последнюю готовую рабочую модель.

Ошибки для обычного пользователя формулировать понятно, без технического стека и внутренних кодов. Подробную информацию записывать в локальные диагностические логи.

## 10. Безопасность и приватность

- Все аудиозаписи обрабатываются локально.
- Текст транскрибации не отправляется на внешние серверы.
- Диаризация выполняется на устройстве.
- Сеть используется только для получения каталога и загрузки файлов моделей.
- Не отправлять на сервер информацию о содержимом пользовательских записей.
- Не запрашивать лишние разрешения Android.
- Проверять загружаемые файлы до их регистрации и запуска.
- Не выполнять произвольный код из пакета модели.
- Не доверять метаданным модели без проверки допустимого формата и структуры.

## 11. Тестирование

### 11.1. Проверка первого запуска

- Установить приложение на чистое устройство.
- Убедиться, что встроенная Whisper-модель доступна.
- Убедиться, что приложение не требует скачивать другую модель.
- Убедиться, что можно сразу импортировать аудио и выполнить транскрибацию.
- Проверить диаризацию через встроенные компоненты.

### 11.2. Проверка каталога

- Получение списка моделей.
- Отображение размеров и статусов.
- Загрузка разных вариантов Whisper.
- Загрузка Parakeet разных размеров и вариантов.
- Загрузка GigaAM v3.
- Загрузка GigaAM v3 Multilingual.
- Обработка отсутствующей сети.
- Повторная попытка после прерванной загрузки.

### 11.3. Проверка подготовки

Для каждой поддерживаемой модели:
- проверка файлов;
- проверка контрольной суммы;
- проверка совместимости;
- инициализация правильного backend;
- тестовый запуск;
- успешная транскрибация короткой записи.

Отдельно проверить:
- GigaAM v3;
- GigaAM v3 Multilingual.

Для каждой из этих моделей необходимо подтвердить, что используется корректная реализация backend и что модель действительно выполняет транскрибацию на устройстве.

Особенно важно проверить, что для Parakeet и обеих моделей GigaAM действительно реализована поддержка соответствующего движка, а не только загрузка файлов и отображение модели в интерфейсе.

### 11.4. Проверка импорта

- Импорт корректной модели.
- Импорт неполного набора файлов.
- Импорт неподдерживаемого формата.
- Отмена импорта.
- Отсутствие свободного места.
- Повторный импорт уже установленной модели.

### 11.5. Проверка удаления

- Удаление дополнительной неактивной модели.
- Попытка удалить последнюю готовую модель.
- Попытка удалить встроенный Whisper.
- Попытка удалить обязательные компоненты sherpa.
- Попытка удалить активную модель во время транскрибации.
- Удаление модели, которая успешно заменена другой.

### 11.6. Проверка офлайн-режима

После установки модели отключить интернет и проверить:
- открытие приложения;
- доступность установленной модели;
- импорт аудиозаписи;
- транскрибацию;
- диаризацию;
- экспорт JSON.

Ни один из этих процессов не должен требовать сетевого соединения.

## 12. Критерии приёмки

Задача считается выполненной, если:

1. Встроенный Whisper продолжает работать без интернета.
2. Встроенные компоненты sherpa-onnx сохранены.
3. При первом запуске пользователь не должен вручную скачивать или выбирать модель.
4. Приложение самостоятельно выбирает готовую подходящую модель.
5. Поддерживается установка моделей из каталога.
6. Поддерживается импорт собственной модели.
7. После установки модель автоматически проверяется, регистрируется и инициализируется.
8. Модель отображается как готовая только после успешной проверки реального запуска.
9. Поддерживаемые семейства Parakeet, Whisper, GigaAM v3 и GigaAM v3 Multilingual подключаются через соответствующие backend.
10. GigaAM v3 и GigaAM v3 Multilingual доступны как отдельные варианты каталога.
11. Дополнительные модели можно удалять с соблюдением ограничений.
12. Невозможно случайно удалить последнюю рабочую модель распознавания.
13. Невозможно удалить обязательные компоненты диаризации.
14. Ошибка загрузки или инициализации дополнительной модели не ломает существующую транскрибацию.
15. После установки модель работает офлайн.
16. Существующий формат результата транскрибации и экспорт JSON продолжают работать.

## 13. Порядок реализации

Реализацию рекомендуется разделить на этапы:

**Этап 1. Аудит существующей архитектуры**
- изучить текущую загрузку Whisper;
- изучить конфигурации sherpa;
- найти все жёстко заданные пути;
- зафиксировать текущий рабочий сценарий транскрибации и диаризации.

**Этап 2. Базовая архитектура Model Manager**
- реализовать ModelRegistry;
- реализовать ModelManager;
- реализовать состояния моделей;
- перенести получение путей к моделям в централизованный компонент;
- сохранить существующий сценарий работы приложения.

**Этап 3. Установка и подготовка моделей**
- реализовать ModelDownloader;
- реализовать ModelImporter;
- реализовать ModelVerifier;
- реализовать ModelInitializer;
- подготовить manifest каталога.

**Этап 4. Поддержка дополнительных backend**
- проверить требования Parakeet;
- реализовать соответствующий адаптер;
- проверить требования GigaAM v3;
- реализовать соответствующий адаптер;
- проверить требования GigaAM v3 Multilingual;
- реализовать соответствующий адаптер;
- обеспечить поддержку разных вариантов Whisper;
- выполнить тестовую транскрибацию каждой поддерживаемой моделью.

**Этап 5. Автоматический выбор и защита**
- реализовать ModelSelector;
- реализовать безопасное переключение;
- добавить резервный переход на встроенный Whisper;
- реализовать правила удаления;
- защитить компоненты диаризации.

**Этап 6. Пользовательский интерфейс**
- добавить раздел управления моделями;
- добавить понятные статусы и прогресс;
- добавить импорт;
- добавить установку из каталога;
- добавить удаление дополнительных моделей;
- скрыть технические детали от обычного пользовательского сценария.

**Этап 7. Проверки**
- выполнить тесты загрузки, импорта, подготовки, переключения и удаления;
- проверить офлайн-работу;
- проверить регрессию транскрибации и диаризации;
- проверить экспорт JSON.

## 14. Ожидаемый результат

В приложении должна появиться надёжная система, которая самостоятельно управляет моделями распознавания.

Пользователь открывает приложение, записывает или импортирует аудио и запускает транскрибацию. Приложение само знает, какая модель готова к работе, использует её и обеспечивает необходимую интеграцию с диаризацией.

Дополнительные модели можно устанавливать и удалять, но пользователь не должен заниматься ручной настройкой нейросетей.

**Ключевое требование: Model Manager управляет моделями ради бесперебойной работы приложения, а не превращает пользователя в администратора нейросетей.**
