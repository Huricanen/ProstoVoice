# DECISIONS

## Принятые решения

### 2026-11-06 — начать с минимального Android-каркаса

- **Контекст:** команда дала команду начать реализацию до получения полного ТЗ.
- **Решение:** создать обратимый Kotlin DSL/Compose-каркас с SAF и контрактом `TranscriptionOrchestrator`, не добавляя модели и native runtime.
- **Основание:** позволяет подготовить UI и границы pipeline без фиксации неизвестных требований.
- **Последствия:** реальная обработка и сборка остаются неподтверждёнными до установки JDK/Gradle/NDK/CMake и подключения моделей.

### 2026-11-06 — изолировать native runtime и сохранить fallback

- **Контекст:** native toolchain и модели пока недоступны.
- **Решение:** JNI boundary и C++ stub не подключаются к Gradle до подтверждения NDK/CMake; UI сохраняет возможность Kotlin/Whisper-only fallback.
- **Основание:** не блокировать проверку UI и контрактов отсутствующими инструментами.
- **Последствия:** native status сейчас stub и не выполняет распознавание.

### 2026-11-06 — зафиксировать Gradle wrapper 8.7

- **Контекст:** системный Gradle отсутствовал, но Android Studio JDK 25 несовместим с текущей Kotlin toolchain.
- **Решение:** добавить Gradle wrapper 8.7 и выполнять сборку на доступном JDK 17.
- **Основание:** `assembleDebug` и `test` успешно завершились на JDK 17.
- **Последствия:** для локальной сборки требуется JDK 17 или совместимый JDK; native toolchain остаётся отдельным блокером.

### 2026-11-06 — начать с потокового PCM WAV decoder

- **Контекст:** native/FFmpeg toolchain и форматный набор ещё не подтверждены.
- **Решение:** реализовать bounded PCM 16-bit WAV decoder с downmix/resampling; оставить MP3/M4A за отдельным MediaCodec adapter.
- **Основание:** WAV-путь не требует внешних native библиотек и покрывает детерминированный smoke test.
- **Последствия:** MP3/M4A и реальные ASR-модели остаются незавершёнными.

### 2026-11-06 — использовать WorkManager для фоновой обработки

- **Контекст:** обработка записи может быть длительной и должна переживать сворачивание Activity.
- **Решение:** передавать URI в offline `OneTimeWorkRequest`, публиковать progress и возвращать структурированные ошибки.
- **Основание:** Android lifecycle и требования offline MVP.
- **Последствия:** длительная обработка вынесена из Activity; полный transcript хранится app-private, а в WorkManager output передаются только metadata и путь к файлу.

### 2026-11-07 — подключить реальный pipeline к WorkManager

- **Контекст:** прямой вызов orchestrator из ViewModel мог быть прерван сворачиванием или уничтожением Activity.
- **Решение:** запускать `WhisperTranscriptionOrchestrator` в `CoroutineWorker`, использовать уникальную offline-задачу `transcription`, публиковать stage/progress и наблюдать состояние через `WorkInfo`.
- **Основание:** сборка/unit-тесты прошли; APK установлен на Poco X7 и приложение запущено.
- **Последствия:** переживание Activity lifecycle подготовлено, но полный device-run с обработкой аудио и восстановлением после закрытия ещё требует отдельной проверки.

### 2026-11-07 — использовать foreground worker для длительной обработки

- **Контекст:** локальная Whisper/diarization обработка может занимать несколько минут и должна продолжаться при свёрнутом приложении.
- **Решение:** `TranscriptionWorker` реализует `getForegroundInfo()`, создаёт notification channel и запускается с `dataSync` foreground service type; прогресс отражается в уведомлении.
- **Основание:** Android ограничивает длительные фоновые задачи; foreground notification даёт системе явный пользовательский сигнал о продолжающейся обработке.
- **Последствия:** требуется постоянное системное уведомление на время обработки и соответствующие foreground service permissions.

### 2026-11-07 — сохранять фактическое время обработки

- **Контекст:** одного текущего таймера в Activity недостаточно после завершения или перезапуска приложения.
- **Решение:** worker измеряет elapsed realtime от начала pipeline до сохранения transcript, пишет `processing_time_ms` в app-private JSON, а UI показывает итог рядом с результатом.
- **Основание:** время измеряется на устройстве и не зависит от сетевых часов или длительности аудио.
- **Последствия:** старые сохранённые результаты без поля показывают `00:00` до следующей обработки.

### 2026-11-07 — уведомлять о завершении фоновой обработки

- **Контекст:** foreground-уведомление предназначено для активной задачи и исчезает после завершения worker, поэтому пользователь не видел явного результата в фоне.
- **Решение:** после успеха или ошибки публиковать отдельное auto-cancel notification; успешное сообщение содержит elapsed time.
- **Основание:** системное уведомление остаётся видимым после удаления foreground service и не требует открытия приложения.
- **Последствия:** добавлен отдельный notification channel для статусов обработки.

### 2026-11-07 — запросить разрешение на уведомления в UI

- **Контекст:** Android 13+ скрывает уведомления без runtime permission; на тестовом Poco состояние старой установки было `ignore`.
- **Решение:** добавить `POST_NOTIFICATIONS` в manifest, запрос при запуске и кнопку открытия системных notification settings.
- **Основание:** стандартный Android permission flow; обновление APK с `-r` не меняет ранее отклонённое разрешение.
- **Последствия:** для старой установки потребуется ручное включение или однократная переустановка с очисткой данных.

### 2026-11-07 — нормализовать labels и адаптировать smoothing для нескольких speakers

- **Контекст:** предоставленный экспорт содержал четыре устойчивых speaker-кластера, но native IDs были разреженными (`speaker_1`, `speaker_3`, `speaker_4`, `speaker_6`), а общий smoothing-порог был рассчитан на диалог из двух человек.
- **Решение:** перенумеровывать labels по порядку появления и ограничивать smoothing до 600 мс при 4+ speakers.
- **Основание:** это устраняет ложное впечатление лишних голосов и сохраняет короткие turn boundaries без confidence-based переназначения.
- **Последствия:** точность embeddings и фактическое число кластеров требуют повторной обработки исходной M4A на телефоне.

### 2026-11-07 — использовать word-level timestamps для speaker alignment

- **Контекст:** правильные diarization intervals могли получать неправильный текст, когда Whisper объединял слова разных участников в один segment.
- **Решение:** включить `token_timestamps` в Whisper.cpp JNI, передавать token intervals в Kotlin и назначать speaker на уровне слов; при отсутствии tokens сохранять прежний fallback.
- **Основание:** временное пересечение слова с speaker interval точнее приблизительного распределения слов по количеству.
- **Последствия:** немного увеличивается объём JNI JSON и время Whisper; требуется device-проверка качества и отсутствие дублей на границах 30-секундных chunks.

### 2026-11-07 — отозвать экспериментальный word-level alignment

- **Контекст:** после включения Whisper token timestamps на новых записях speaker assignment стал существенно хуже, а worker начал завершаться с гонкой progress callbacks.
- **Решение:** вернуть segment-level alignment и убрать token timestamps из runtime; сохранить идею word-level для отдельного офлайн-исследования с проверкой качества.
- **Основание:** наблюдаемая регрессия на реальных пользовательских записях важнее непроверенного улучшения.
- **Последствия:** точность назначения внутри одного длинного ASR segment остаётся ограничением; сначала требуется исправить базовый diarization/alignment и собрать диагностические данные.

### 2026-11-07 — сериализовать публикацию progress worker

- **Контекст:** callback native pipeline вызывал `setProgressAsync` параллельно с завершением worker.
- **Решение:** callback только записывает последнее состояние, отдельный coroutine monitor публикует progress и foreground notification последовательно; monitor отменяется и дожидается завершения до возврата `Result`.
- **Основание:** текст ошибки Android прямо указывает на незавершённый `setProgressAsync` при возврате результата.
- **Последствия:** notification обновляется примерно раз в 500 мс, а не на каждый callback.

### 2026-11-07 — заменить speaker embedding на WeSpeaker VoxCeleb ResNet34

- **Контекст:** ERes2Net 3D-Speaker давал нестабильное назначение реплик участникам на русских многоголосых записях; segmentation уже использовал pyannote 3.0 через sherpa-onnx.
- **Решение:** оставить sherpa-onnx и pyannote segmentation, заменить только embedding-модель на официальный `wespeaker_en_voxceleb_resnet34.onnx` из release `speaker-recongition-models`.
- **Основание:** модель совместима с sherpa embedding loader, содержит metadata `framework=wespeaker`, `sample_rate=16000`, обучена на VoxCeleb и не является китайским 3D-Speaker export.
- **Последствия:** размер embedding asset уменьшен примерно с 39.6 MB до 26.5 MB; качество на конкретных русских записях нужно подтвердить сравнительным прогоном.

### 2026-11-07 — откатить WeSpeaker после device-регрессии

- **Контекст:** после замены embedding-модели на Poco X7 результат diarization перестал разделять участников и схлопнулся в один cluster.
- **Решение:** вернуть ERes2Net 3D-Speaker как runtime baseline, WeSpeaker оставить только в `models/optional` для отдельной настройки threshold.
- **Основание:** подтверждённый device-регресс при текущих параметрах важнее потенциального выигрыша от неподобранной модели.
- **Последствия:** качество остаётся нерешённой задачей; следующая попытка должна включать явный `num_clusters` или отдельный threshold profile.

### 2026-11-06 — принять JSON-контракт презентации

- **Контекст:** текущий внутренний экспорт использовал имена полей Kotlin-модели.
- **Решение:** внешний JSON содержит корневой массив `transcript`, а сегмент — `speaker_id`, `start_ms`, `end_ms`, `text`.
- **Основание:** формат из обязательного задания хакатона.
- **Последствия:** внутренние `sourceName`, `durationMs` и `language` не экспортируются в базовом JSON.

### 2026-11-06 — не выдавать placeholder за обработку

- **Контекст:** real Whisper/sherpa-onnx runtime и модели ещё не доступны.
- **Решение:** placeholder orchestrator завершает задачу структурированной ошибкой и не возвращает пустой успешный transcript.
- **Основание:** ТЗ запрещает подменять работу модели заранее подготовленным результатом.
- **Последствия:** APK до подключения моделей честно показывает ограничение backend.

### 2026-11-06 — вынести WER/RTF в воспроизводимый evaluation tool

- **Контекст:** хакатон оценивает три одинаковые записи по WER и RTF.
- **Решение:** хранить расчёт в `tools/evaluate_transcript.py`, принимающем reference/hypothesis JSON и время обработки.
- **Основание:** единый локальный способ сравнения результатов после подключения моделей.
- **Последствия:** реальные значения появятся после получения трёх тестовых записей и эталонов.

### 2026-11-06 — сохранить репозиторий лёгким до получения ТЗ

- **Контекст:** исходники и точные требования ещё отсутствуют.
- **Решение:** не добавлять в Git Android-каркас, native-библиотеки или модели до уточнения ТЗ; подготовить только документацию и безопасный `.gitignore`.
- **Основание:** требуется избежать ранней фиксации несовместимых решений и разрастания репозитория.
- **Последствия:** реализация и точные команды сборки пока невозможны.

### 2026-11-06 — использовать Whisper.cpp GGML Large-v3 Q5 вне Git

- **Контекст:** команда выбрала Whisper Large, а тестовый телефон имеет около 4 ГБ RAM.
- **Решение:** native pipeline собирается с Whisper.cpp; модель `ggml-large-v3-q5_0.bin` включается в APK как uncompressed asset и при первом использовании извлекается в app-specific `files/models`.
- **Основание:** Q5-модель совместима с Whisper.cpp и существенно снижает RAM/диск относительно full precision; размер APK пока не ограничен, но воспроизводимая упаковка ещё не выбрана.
- **Последствия:** debug APK увеличился примерно до 1.1 ГБ, а на первом запуске требуется дополнительное место под распакованную модель; реальная скорость и RAM требуют device benchmark.

### 2026-11-06 — использовать официальный sherpa-onnx pyannote export

- **Контекст:** приложение завершалось при первом запуске diarization без Java stack trace.
- **Решение:** заменить segmentation ONNX из `onnx-community` на `model.int8.onnx` из релиза sherpa-onnx `speaker-segmentation-models`; добавить native logs и сериализацию diarization вызовов.
- **Основание:** loader sherpa-onnx требует семь metadata-полей (`sample_rate`, `window_size`, `receptive_field_size`, `receptive_field_shift`, `num_speakers`, `powerset_max_classes`, `num_classes`) и завершает процесс при их отсутствии; официальный export содержит эти поля.
- **Последствия:** статическая совместимость исправлена, но успешность inference и нагрузка на телефон должны быть подтверждены отдельным device smoke test.

### 2026-11-07 — повысить устойчивость speaker clustering

- **Контекст:** на первом успешном device run диалог с двумя участниками дал пять speaker labels и слишком много коротких переключений.
- **Решение:** увеличить FastClustering distance threshold с `0.35` до `0.75`, минимальные интервалы speech activity до `0.4/0.3s`, а alignment smoothing — до `1.2s`.
- **Основание:** документация sherpa-onnx указывает, что больший threshold создаёт меньше кластеров; короткие переключения сглаживаются перед объединением соседних реплик.
- **Последствия:** автоматическое число speakers сохранено; точность параметров требует повторной проверки на реальном диалоге.

### 2026-11-07 — обрабатывать длинные записи чанками Whisper

- **Контекст:** передача всей длинной записи в один Whisper inference повышает время обработки и пиковую нагрузку памяти.
- **Решение:** использовать последовательные окна по 30 секунд с overlap 2 секунды, сдвигать timestamps в абсолютную шкалу и удалять повторяющиеся ASR-сегменты на границах окон.
- **Основание:** Whisper работает в ограниченном временном контексте; overlap сохраняет слова на границе, а последовательная обработка не создаёт дополнительной конкуренции за RAM.
- **Последствия:** diarization пока получает полный PCM и сохраняет глобальную согласованность speaker labels; отдельное потоковое diarization требует следующего этапа.

### 2026-11-07 — сохранять последний результат атомарно

- **Контекст:** падение или перезапуск приложения сбрасывал отображаемый transcript.
- **Решение:** после успешной обработки сохранять полный transcript в app-private JSON через временный файл и атомарное переименование; восстанавливать его при создании ViewModel.
- **Основание:** не требует сети и переживает закрытие Activity или процесса.
- **Последствия:** сохраняется только последний завершённый результат; история нескольких записей пока не входит в MVP.

### 2026-11-07 — показывать ход длительной обработки

- **Контекст:** локальный Whisper и diarization могут занимать минуты, а одного индeterminate spinner недостаточно для понимания состояния.
- **Решение:** ViewModel показывает elapsed timer и determinate progress: подготовка/decode, доля Whisper-чанков, diarization и финализация; UI также отображает текущий этап.
- **Основание:** прогресс Whisper-чанков измерим напрямую, а остальные стадии имеют явные границы.
- **Последствия:** процент является оценкой по стадиям и не отражает точное оставшееся время diarization.

### 2026-11-07 — учитывать хвост короткой финальной реплики

- **Контекст:** Whisper иногда растягивает timestamps финального короткого сегмента в предыдущую реплику, и выбор только по максимальному overlap назначает speaker неверно.
- **Решение:** для последнего ASR-сегмента длительностью до 2.5 секунды предпочитать speaker, покрывающий последние 500 мс, если там есть минимум 150 мс diarization evidence.
- **Основание:** конец сегмента лучше отражает speaker короткой финальной реплики; правило ограничено только финальным коротким сегментом.
- **Последствия:** добавлен unit test; корректность на конкретной записи нужно подтвердить повторной обработкой на телефоне.

### 2026-11-07 — делить ASR-сегмент при смене speaker

- **Контекст:** Whisper может объединить две соседние фразы разных людей в один ASR-сегмент, из-за чего overlap alignment назначает весь текст одному speaker.
- **Решение:** при наличии diarization boundary внутри ASR-интервала и достаточного числа слов разделять интервал и распределять слова по получившимся временным частям.
- **Основание:** сохраняется полный текст, а speaker labels соответствуют границам diarization; короткие однословные сегменты не делятся.
- **Последствия:** разбиение слов по времени приблизительное, поскольку текущий Whisper JNI возвращает segment-level timestamps без word timestamps.

### 2026-11-07 — заполнять короткие gaps diarization

- **Контекст:** после split по speaker boundaries короткие промежутки без diarization evidence отображались как `UNKNOWN`.
- **Решение:** для gap до 1 секунды выбирать ближайший предыдущий или следующий speaker; более длинные gaps оставлять `UNKNOWN`.
- **Основание:** интервалы на скриншоте были техническими паузами 54–846 мс, а не отдельными неизвестными голосами.
- **Последствия:** добавлен unit test; реальная запись должна быть перепроверена новым APK.

## Ожидают проверки или уточнения

Минимальный Android API, ABI, формат поставки моделей, модель Whisper Large и квантование, memory budget 4 ГБ устройства, RealTime scope, лицензии моделей, входные форматы и правила WER/RTF требуют проверки или уточнения. Базовая функциональность из презентации уже принята в работу.

## Требования среднего уровня, отложенные после базы

После прохождения базы можно добавлять предобработку, фильтрацию пауз, пунктуацию, улучшенную устойчивость speaker labels, progress/playback enhancements и RealTime. Эти функции не должны блокировать обязательную проверку.

# 2026-11-07 — зафиксировать пользовательский эталон для диаризации

- **Контекст:** качество diarization нельзя надёжно настраивать по единичным визуальным наблюдениям; для сравнения нужен повторяемый reference с временными границами и текстом.
- **Решение:** хранить ручную разметку записи `07.11.2026 13.40.m4a` в `evaluation/diarization/07.11.2026-13.40.reference.json` в текущем JSON-контракте `transcript`, с четырьмя speaker ID и восемью интервалами.
- **Основание:** интервалы и текст предоставлены пользователем как эталон; исходные опечатки и формулировки сохранены без редакторских исправлений.
- **Последствия:** fixture можно использовать для будущих метрик и device regression; сам аудиофайл и фактический runtime output в Git не добавляются, а качество пока не считается подтверждённым до прогона на Android.

# 2026-11-07 — считать baseline-метрики локальным interval evaluator

- **Контекст:** автоматические speaker labels не обязаны совпадать с ручными номерами, поэтому прямое сравнение ID даёт ложные ошибки.
- **Решение:** использовать 10-мс сетку и оптимальное сопоставление labels перед расчётом DER; отдельно выводить пропущенную речь, false alarm, confusion и число переключений.
- **Основание:** метрики сравнивают временное поведение diarization, а не случайные имена кластеров; evaluator запускается локально и не требует Android runtime.
- **Последствия:** DER станет доступен после получения фактического JSON из device-прогона; текущие результаты без такого JSON не считаются измерением качества.

# 2026-11-07 — сделать параметры diarization профилем

- **Контекст:** threshold и длительности speech activity нужно подбирать на одном baseline, а изменение native-констант затрудняет воспроизводимое сравнение.
- **Решение:** передавать в JNI `numClusters`, clustering threshold и `minDurationOn/Off` через валидируемый `DiarizationConfig`; значения по умолчанию оставить текущими.
- **Основание:** конфигурационный профиль позволяет делать A/B и sweep без изменения алгоритма и сохраняет существующий runtime behavior.
- **Последствия:** параметры теперь можно подключить к UI или offline sweep; фактическое влияние профилей ещё требует device-прогона.

# 2026-11-07 — отклонить уменьшение шага окон segmentation

- **Контекст:** первый device-прогон дал 14 raw-сегментов и пропустил границы между короткими репликами.
- **Решение:** вернуть `windowShiftRatio=0.1` как runtime default; сохранить параметр и raw interval logging для отдельных экспериментов.
- **Основание:** device-прогон с `0.05` занял 233 секунды и дал 5 speakers/17 raw-сегментов, то есть не улучшил подтверждённый baseline.
- **Последствия:** следующий эксперимент изолирует clustering, задав `numClusters=4` для записи с четырьмя известными участниками.

# 2026-11-07 — зафиксировать число кластеров для эталонного диалога

- **Контекст:** автоматический clustering на эталонной записи дал 5 speakers при ручной разметке 4 участников.
- **Решение:** runtime profile по умолчанию использует `numClusters=4`; `numClusters=0` остаётся доступным для будущего режима неизвестного числа speakers.
- **Основание:** число участников в предоставленном baseline задано пользователем и позволяет проверить, является ли лишний кластер причиной текущей ошибки.
- **Последствия:** default profile оптимизирован под текущий benchmark; перед расширением на записи с неизвестным числом speakers потребуется отдельный профиль.

# 2026-11-07 — снизить clustering threshold для проверки разделения embeddings

- **Контекст:** при `numClusters=4` и threshold `0.75` sherpa-onnx вернул только 3 фактических speakers, а DER вырос до `0.2997`.
- **Решение:** следующий профиль использует threshold `0.5` при том же фиксированном числе кластеров и `windowShiftRatio=0.1`.
- **Основание:** более низкий threshold должен уменьшить агрессивное слияние embedding-кластеров; значение `0.5` используется в примерах sherpa-onnx для фиксированного числа speakers.
- **Последствия:** это диагностический эксперимент, а не подтверждённое улучшение; после device-прогона профиль будет принят или отклонён по DER.

# 2026-11-07 — проверить WeSpeaker при фиксированном числе кластеров

- **Контекст:** ERes2Net дал одинаковые raw intervals при threshold `0.75` и `0.5`, а фактически вернул 3 speakers вместо 4.
- **Решение:** следующий APK использует уже загруженную `wespeaker-en-voxceleb-resnet34.onnx` при `numClusters=4`; ERes2Net остаётся доступным для отката.
- **Основание:** сравнение изолирует embedding-модель от segmentation и alignment, которые остаются неизменными.
- **Последствия:** прошлый WeSpeaker-прогон с автоматическим числом кластеров был отклонён, поэтому этот эксперимент нельзя считать подтверждением улучшения до device-метрик.
